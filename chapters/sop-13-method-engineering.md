# SOP-13: 方法工程与采纳（Method Engineering & Adoption）

> **定位**: 团队引入、裁剪、维护任何建模方法/模板/流程时的元方法——用 DPR 元模型与三规则保证方法"赋能而非指令"，拒绝货物崇拜与方法大泥球 | **组**: E | **主要来源**: DPR.md 全文（Zimmermann, 2020–2023）；MDSL §10.5；ICWE 主题演讲工具箱页

## 何时启用

当你面对的不是"一个建模问题"而是"**方法本身的问题**"时启用：

- 团队要引入新的建模方法、模板、流程或 SOP（包括本 SOP 库的本地化）；
- 现有方法被抱怨"文书负担太重"、没人用或只在检查时应付；
- 方法执行出现货物崇拜迹象——照抄模板却说不清目的；
- 需要评审/裁剪第三方方法论、咨询方案或内部规范。

本 SOP 是全库的**元 SOP**：SOP-01~12 每一个都是"方法元素"，它们的引入、裁剪与退役都应经过本流程。方法工程师的第一信条：*我们都从错误中学习——但这些错误非得是我们自己的吗？* 好方法让你把时间花在领域与技术的具体问题上，而不是反复发明文档结构与记法。

## 触发条件

1. **新方法/模板提案** — 有人提议引入新的需求模板、评审流程、建模记法或工具方法链；
2. **文书负担抱怨** — 团队反馈"填表时间超过设计时间"、模板字段大半用不上；
3. **货物崇拜迹象** — 执行者无法回答"这个模板字段为什么存在/为谁服务"；
4. **合规表演** — 方法产出只为通过检查，检查一过无人再看；
5. **SOP 库维护节点** — 定期（如每季度）对既有方法元素做保留/裁剪/退役评审。

## 完整步骤

### 步骤 1：按元模型归位（五元组）

DPR 的方法域模型：**角色（Role）执行活动（Activity），活动由技术（Technique）与模板（Template）支持，产出工件（Artifact）**。

对每个待引入的方法元素先问：它是哪一类？

| 元模型元素 | 判定问题 | 例子 |
|-----------|---------|------|
| 角色 | 谁来做？目标受众明确吗？ | 业务分析师、软件架构师 |
| 活动 | 有步骤的过程？ | 分步服务设计（契约优先）、SMART NFR 引导 |
| 技术 | 有诀窍的手法？ | 故事拆分手法、CRC 协作走查 |
| 模板 | 有结构的格式？ | 极简用例模板、Y-statement |
| 工件 | 有产出的结果？ | 候选端点清单、架构决策记录 |

归位失败（五类都不是）→ 大概率是“方法大泥球”候选，进步骤 2 严审。

### 步骤 2：三规则过滤

方法工程与采纳的三条规则（DPR 原文规则，逐条过）：

1. **上下文至上（Context matters）** — 在一个环境中好用的东西，换个环境可能是 headache 的主要来源。通用建议必须**显式写明适用上下文、使用条件与局限**。→ 检查：提案里有没有“何时适用/何时不适用”？没有就打回补写。
2. **有疑就删（If in doubt, leave it out）** — 不造“方法大泥球”（big ball of method mud）；模板必须有**明确目标受众及其信息需求**；发布前自己先用一遍。→ 检查：每个字段/步骤能指认受众吗？指认不了就删。
3. **目的/有用性高于合规（Value purpose over compliance）** — 不照本宣科遵循模板与流程，按自身需要**改造（adopt/adapt）**；拒绝盲从与货物崇拜。→ 检查：提案是否允许裁剪？“必须原样执行”者默认拒收。

### 步骤 3：态度校验（Enabling vs. Directing）

方法应当持**赋能型态度（Enabling Attitude）**而非**指令型态度（Directing）**——"我把方法视为导游（tour guide），而不是律师（lawyer）"。

自检法（DPR 作者的自实验，可直接照做）：全局搜索方法文本中的“**必须**/must/have to”类断言措辞：

- 允许出现的位置：模板填写说明、贡献规范（对方法工程师自己可以更强硬）；
- 不允许出现的位置：方法内容本身。方法内容应是建议、提示、"何时用 X"式指引，并附正反用例（什么让一个实例有用/没用）。

措辞满篇"必须"的方法催生合规表演；赋能型方法才会被真正采纳。

### 步骤 4：Mighty Methods 五判据评审（Keeling）

按 Michael Keeling 的"强大方法"五判据打分（每项：满足/部分/不满足 + 一句话证据）：

1. **促进人本设计** — 目标受众明确（DPR：架构师与开发者，开发者体验 DX 要紧）；
2. **偏向具体产出** — 有工件/模板级产出，非理念宣讲；警惕以卖服务/课程为动机的“方法”
3. **覆盖整个设计空间** — 从（非）功能需求到架构决策到架构建模的链路完整（部署/运维至少被提及）；
4. **促进团队成长** — **无需太多额外辅导**即可应用，含“什么让实例有用/没用”的提示；
5. **易教好用** — 能在培训/工作坊中教授，有具体示例与动机故事支撑。

五判据中 ≥2 项"不满足"→ 拒绝引入或退回重造。

### 步骤 5：轻量工件优先

通过前四步后，优先用**轻量工件库**落地，而非重型文档体系：

| 轻量工件 | 结构与用途 |
|---------|-----------|
| **Y-statement**（Y 型架构决策记录） | 一句话捕获决策及其理由（权衡两侧后选定一边，形如"在…上下文中，面对…问题，为了…收益选择了…方案，接受…代价"） |
| **极简用例模板** | `Pre: 前置条件 / 1. 用户… / 2. 系统… / Post: 后置条件`——够瘦（lean enough）才能被持续使用 |
| **SMART NFR** | 非功能需求按 Specific（具体）、Measurable（可测）、Agreed upon（达成一致）、Realistic（现实）、Time bound（有时限）表述 |
| **CRC 卡** | 组件（Component）、职责（Responsibility）、协作（Collaboration）——指定组件及其协作关系 |
| **四步架构建模** | 上下文图（黑盒）→ 架构总览图 → 组件图 → 部署图；前三步与 C4 模型的 context/container/component 图对齐，第四步取运维视角 |

参考体量：DPR v1.4 全部家当 = 2 个角色、8 项活动、15 个工件模板（模板兼作检查清单）。**方法库的大小不是美德，被使用才是。**

### 步骤 6：试点与采纳决策记录

- 发布前**自己先用一遍**（规则 2 的要求）：挑一个真实故事/一次真实评审做试点；
- 试点后写采纳决策记录（就用 Y-statement）：引入了什么、裁剪了什么、为什么、接受什么代价；
- 设定复盘点（如 3 个迭代后）：使用率、文书负担感、产出质量三问。

### 步骤 7：持续修剪（退役机制）

定期评审既有方法元素：连续两个周期无人使用 → 询问原因 → 修（补上下文/减字段）或删。有疑就删同样适用于**已入库**的元素。方法库是花园，不是仓库。

## 使用示例

**场景**：团队被推销一份 40 字段的"需求规格说明书模板"，要求所有需求"必须"按此填写。

按步骤走一遍：

1. **归位**：它是一个"模板"（服务于一项"需求捕获"活动，受众是业务分析师）——归位成立；
2. **三规则**：①无适用上下文说明（小需求也全量填 40 字段？）→ 违反规则 1；②14 个字段指认不出读者 → 违反规则 2，删；③“必须原样填写、不许裁剪” → 违反规则 3，拒收原案；
3. **态度校验**：全文搜"必须"出现 17 次，全部在方法内容里 → 指令型态度，改写为"当需求涉及多方集成时，建议补充 X 段"式指引；
4. **五判据**：人本设计（受众模糊，✗ 部分）、具体产出（✓）、全设计空间（只覆盖需求段，✗）、团队成长（需专职培训，✗）、易教好用（✗）→ 4 项不达标，原模板拒绝引入；
5. **轻量替代**：改配"用户故事 + 极简用例模板（Pre/步骤/Post）+ SMART NFR + Y-statement"组合，一页纸覆盖原模板的有效信息；
6. **试点与记录**：拿本迭代 3 个故事试用，Y-statement 记录："在需求文档合规审查的上下文中，面对 40 字段模板的文书负担，为了保持敏捷节奏选择了轻量工件组合，接受审计时需额外汇总说明的代价。"
7. **复盘**：3 个迭代后使用率 100%、无合规投诉 → 转正入库。

**场景 2（本库自维护）**：新增 SOP 提案必须附带：五元组归位、适用上下文与局限、目标受众、可裁剪声明——SOP-13 管辖 SOP-01~12 的准入。

## 技术交付物

1. **方法元素卡** — 每个入库元素一张：五元组归位（角色/活动/技术/模板/工件）+ 适用上下文与局限 + 目标受众 + 裁剪说明；
2. **采纳决策记录（Y-statements）** — 每次引入/裁剪/退役一条，含接受的代价；
3. **态度检查结果** — "必须/must/have to"扫描位置清单（应只出现在填写说明与贡献规范中）；
4. **五判据评审表** — 五项各附一句话证据；
5. **试点复盘记录** — 使用率/负担感/产出质量三问的答案。

## 成功标准

- [ ] 每个方法元素有**明确目标受众与适用边界**（何时用/何时不用写在元素卡上）；
- [ ] 团队能在**无额外辅导**下上手（五判据第 4 项达标；试点期提问集中在领域问题而非模板填法）；
- [ ] "必须"类措辞仅出现在贡献规范与填写说明中，**方法内容零指令腔**；
- [ ] 每次引入/裁剪/退役都有 Y-statement 决策记录可查；
- [ ] 方法库有退役机制且在运转（存在被修剪掉的元素，而不仅是新增）。

## 反模式

| 反模式 | 后果与纠正 |
|--------|-----------|
| **方法大泥球** | 无目标受众的大全模板无人使用 → 有疑就删，每字段指认受众 |
| **指令型方法态度** | "必须"满天飞催生合规表演，检查一过全部作废 → 赋能型改写：导游而非律师 |
| **货物崇拜** | 照抄模板说不出目的 → 规则 3：目的高于合规，允许并要求裁剪 |
| **无上下文的通用建议** | 在甲团队有效的做法硬推到乙团队变成 headache → 规则 1：显式适用条件与局限 |
| **发布前不自用** | 模板发下去才发现填不动 → 规则 2 后半句：自己先测试你的创造物 |
| **方法即商品** | 以卖课/卖咨询为主要动机的"方法"，产出服务于转化而非设计 → 五判据第 2 项一票否决 |
| **只增不删** | 方法库膨胀 → 文书负担 → 整体被抛弃；纠正：步骤 7 定期修剪，退役是常态 |
